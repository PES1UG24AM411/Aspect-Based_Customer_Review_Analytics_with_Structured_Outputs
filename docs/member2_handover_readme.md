## Member 2 handover: LLM integration and structured ABSA extraction

This repository contains Member 1's completed preprocessing stage and Member 2's
10-review ABSA extraction pilot implementation. The processed CSV, preprocessing
source, and preprocessing tests are preserved. The extraction implementation does
not rewrite the raw or processed dataset.

## 2. Requirements and installation

Python 3.10 or newer is required. From the repository root:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

`requirements.txt` installs pandas, Lingua (needed by the preserved preprocessing
tests), pytest, Pydantic v2, the OpenAI Python SDK, and python-dotenv. Installation
requires package-index/network access the first time. The tests and preflight do not
require API credentials.

## 3. Offline verification (no API key, no API calls)

Run all repository tests after dependencies are installed:

```bash
python -m pytest -q
```

Run the Member 2 extraction tests alone:

```bash
python -m pytest -q tests/test_extraction.py
```

Validate the local dataset, required columns, prompt file, SHA-256 and exact pilot
selection without creating an API client or making an API request:

```bash
python -m src.extraction.pipeline --preflight
```

This writes `reports/offline_preflight_manifest.json`. The preflight command is safe
to run with `OPENAI_API_KEY` unset. It does not create predictions or call the API.

## 4. API setup (required only for the model pilot)

Create a local environment file:

```bash
cp .env.example .env
```

Edit `.env` and set your API key locally:

```dotenv
OPENAI_API_KEY=your_api_key_here
OPENAI_MODEL=gpt-6-luna
```

Do not commit `.env`, paste the key into source code, or share it in project
messages. `.env` is ignored by `.gitignore`. A ChatGPT subscription and API billing
are separate. Your API project must have billing and model access enabled.

The configured model identifier `gpt-6-luna` is listed on OpenAI's API pricing page.
The pricing page is not proof that a particular API project has access; model
availability, account limits and billing must be checked in that API project.
The implementation uses the OpenAI Responses API Python SDK's Pydantic structured
parsing interface. No API request has been made as part of this handover.

## 5. Run the 10-review pilot (API-dependent)

After `.env` is configured and dependencies are installed, run exactly:

```bash
python -m src.extraction.pipeline
```

The CLI is fixed to the first 10 English reviews. It rejects other `--limit` values
and refuses `--full`. Do not change this guard or run full-dataset extraction until
the team has reviewed and approved the pilot. Resume only processes unfinished
records from the same fixed 10-review cohort.

## 6. Output files

Generated by offline preflight:

- `reports/offline_preflight_manifest.json` — dataset hash, required setup checks,
  English row count, fixed pilot IDs and confirmation that no API call was made.

Generated only after API-backed pilot execution:

- `data/extracted/pilot_predictions.jsonl` — one validated structured record per
  successful review; each line includes original review/product IDs and unchanged
  review text.
- `data/extracted/pilot_failures.jsonl` — review ID, failure category, attempts,
  error type and error message for exhausted failures.
- `reports/pilot_run_manifest.json` — model, prompt/schema versions, dataset hash,
  success/failure/no-aspect counts, token usage, estimated cost and latency.

An illustrative, synthetic schema-only record is stored at
`examples/schema_example.synthetic.jsonl`; it is not a prediction.

## 7. Output schema and validation

Each successful record contains `schema_version`, `review_id`, `product_id`,
`review_text`, `aspects`, and `extraction_status`. Each aspect contains `aspect_id`,
normalized `aspect_term`, `sentiment` (`positive`, `negative`, or `neutral`), exact
source-substring `evidence`, `complaint_present`, and `complaint_evidence`.

Evidence must be an exact substring of the original review. Source IDs and review
text must remain unchanged. Aspect IDs must be unique within a review. Complaint
evidence is required when `complaint_present` is true and must be null otherwise.
An empty aspect list is valid. Negative sentiment alone does not imply a complaint;
complaints must be explicit. Ratings are not passed to the model. The versioned
prompt covers product attributes and non-product experience aspects including
shipping, packaging, seller service and customer support.

Pydantic v2 validates structure; semantic validators verify source identity and
exact evidence. The extractor makes up to three semantic attempts with validation
feedback. Transient rate-limit, timeout, connection and server failures have a
separate bounded retry loop. Authentication/permission failures stop execution.
Invalid or exhausted records are logged rather than silently converted to empty
aspect lists. Existing valid pilot records are used for resume.
